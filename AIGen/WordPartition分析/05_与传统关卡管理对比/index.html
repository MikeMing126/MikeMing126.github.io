05 - 与传统关卡管理对比

基于 UE 5.7 源码对比 World Partition、Level Streaming 和传统 Sub-level 方案

一、传统关卡管理方案

1.1 单一 Persistent Level

最简单的方案：所有内容放在一个关卡中。

优点 缺点
简单直接 内存占用不可控
无加载边界问题 不适合大世界
无版本控制冲突（单人） 无法按需加载

1.2 Sub-levels（子关卡）

将世界拆分为一个 Persistent Level + 多个 Sub-level。

1.3 Level Streaming（关卡流式加载）

通过蓝图或 C++ 代码动态加载/卸载子关卡。

3.1 架构对比

四、适用场景分析

4.1 何时使用 Sub-levels

  • 小型项目（单个关卡即可容纳）
  • 关卡之间有明确的切换（如菜单→游戏→结算）
  • 不需要开放世界体验
  • 团队规模小，无协作需求

4.2 何时使用 Level Streaming

  • 中大型项目
  • 需要按区域加载但世界不太大
  • 需要精确控制加载时机（如进入建筑物时加载室内）
  • 已有 UE4 项目不想大幅重构

4.3 何时使用 World Partition

  • 大世界/开放世界项目
  • 需要无缝大地图体验
  • 团队多人协作编辑
  • 需要运行时动态内容层（Data Layer）
  • 新项目（UE5+）

Level Streaming Volume 的功能在 World Partition 中可以通过以下方式替代：

六、混合使用

World Partition 可以与传统 Level Streaming 共存：

  • World Partition 管理大世界的空间分区
  • ULevelStreamingDynamic::LoadLevelInstance() 仍可用于动态加载独立的关卡实例
  • Level Instance Actor 可以在 World Partition 世界中使用

七、性能对比

7.1 内存

方案 内存特性
Sub-levels（全加载） 最高（所有内容常驻内存）
Level Streaming 中等（按关卡加载，粒度粗）
World Partition 最低（按 Cell 加载，粒度细）

7.2 加载频率

方案 加载频率
Sub-levels 无运行时加载
Level Streaming 低（Volume 触发）
World Partition 高（每帧检查 Streaming Source）

7.3 编辑器性能

方案 编辑器性能
Sub-levels 好（关卡独立编辑）
Level Streaming 好（关卡独立编辑）
World Partition 需要启用 Streaming（超大世界）

八、小结

方案 适用场景 优势 劣势
Sub-levels 小项目 简单 不支持大世界
Level Streaming 中型项目 灵活控制 手动管理，粒度粗
World Partition 大世界/开放世界 自动化，细粒度，协作友好 学习曲线，调试复杂

对于新的大世界项目，强烈推荐使用 World Partition。对于需要精确控制加载时机的场景（如进入建筑物），可以结合 Level Instance 或 Data Layer 实现。
