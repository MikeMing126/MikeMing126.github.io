虚幻引擎 5.7 移动与 Transform 机制深度分析

基于 UE5.7.4 源码的全面调研报告

一、引言：虚幻与传统游戏项目的移动模拟对比

1.1 传统游戏项目的移动模拟

在普通的游戏项目中，移动模拟通常采用如下简洁模型：

核心要素只有三个：位置（Position）、速度（Velocity）、时间（DeltaTime）。这种方式简单直接，但在面对复杂场景时存在诸多不足：

  • 无碰撞处理：需要自行实现碰撞检测和响应
  • 无层级变换：角色站在移动平台上时需要手动处理坐标系转换
  • 无网络同步：多人游戏中的位置同步需要额外设计
  • 无状态管理：行走、飞行、游泳、下落等不同运动模式的切换需要自行管理
  • 无动画驱动：Root Motion（根运动）无法自然融入移动系统

1.2 虚幻引擎的设计思路

虚幻引擎采用了一套分层架构来处理移动和 Transform，从底层到上层依次为：

层级 核心类 职责
基础 Transform 层 USceneComponent 管理组件的空间变换（位置、旋转、缩放）和层级关系
碰撞移动层 UPrimitiveComponent / MoveComponent 处理带碰撞检测的移动（Sweep）
Actor 封装层 AActor 提供角色级别的位置/旋转设置接口
运动组件层 UMovementComponent 系列 实现各种移动模式的物理模拟
物理引擎层 FBodyInstance / Chaos 物理模拟驱动的移动
网络同步层 FRepMovement / 预测系统 多人游戏中的移动同步

这种设计的核心思想是：将移动从”简单的位置计算”提升为”涉及碰撞、物理、动画、网络的系统工程”。

3.3 UPrimitiveComponent::MoveComponentImpl（碰撞版本）

这是真正复杂的移动实现，支持 Sweep（扫描碰撞检测）：

Sweep 的工作原理：

  1. 从 TraceStart 到 TraceEnd 进行形状扫描
  2. 如果遇到阻挡（Blocking Hit），移动到碰撞点而非目标点
  3. 如果是初始穿透（bStartPenetrating），选择法线最相反的碰撞面推出
  4. 移动完成后更新 Overlap 状态

源码参考：PrimitiveComponent.cpp:3042-3191

碰撞检测 ✅ 执行 ✅ 执行

5.7 子步迭代（Substep）机制

虚幻的移动系统不是简单地用一整个 DeltaTime 做一次计算，而是采用了子步迭代：

为什么需要子步？

  • 防止高速运动时穿墙（每步移动距离受限）
  • 在碰撞后精确回退剩余时间（碰撞后退还 remainingTime 继续模拟）
  • 支持模式切换时的时间继承（如从行走到下落，剩余时间在新模式中继续）

九、设计思想总结

9.1 虚幻移动系统 vs 传统 position += velocity * dt 的本质区别

维度 传统方式 虚幻方式
碰撞 无 MoveComponent Sweep 碰撞检测
时间 整帧一次 子步迭代（Substep）
层级 无 组件 Attach 层级变换传播
模式 无 多种 MovementMode 状态机
动画 无 Root Motion 驱动移动
物理 无 力/冲量 → 物理引擎积分
网络 无 客户端预测 + 服务端校正
平台 无 Based Movement（站在移动物体上）
安全 无 扫描碰撞 + 初始穿透处理

9.2 核心设计原则

  1. 分层解耦：Transform 设置、碰撞移动、物理模拟、网络同步各自独立
  2. 组合优于继承：通过 MovementComponent 组件模式实现不同移动行为
  3. 惰性更新：ConditionalUpdateComponentToWorld 避免不必要的 Transform 计算
  4. 延迟更新：FScopedMovementUpdate 允许批量移动后一次性更新
  5. 子步迭代：确保高速运动和碰撞时的稳定性
  6. 状态机模式：通过 MovementMode 清晰地管理不同运动状态
  7. 预测-验证：网络移动的客户端预测机制降低延迟感知
  8. 事件驱动：TransformUpdated 广播、OnUpdateTransform 回调实现松耦合
