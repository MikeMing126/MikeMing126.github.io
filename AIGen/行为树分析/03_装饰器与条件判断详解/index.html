装饰器与条件判断详解

基于 UE 5.7.4 源码，深入分析行为树的装饰器机制和条件判断系统。

一、装饰器概述

装饰器（Decorator）是行为树中的条件判断节点，挂载在复合节点与子节点的连线上，用于控制子节点是否可以执行。装饰器不仅提供静态条件判断，还支持动态的流程中止（Flow Abort），是实现响应式 AI 的关键机制。

1.1 装饰器的角色

装饰器的作用：

  1. 条件守卫：决定子节点是否可执行
  2. 流程中止：条件变化时动态切换执行分支
  3. 状态通知：感知分支的激活/失活事件

这是装饰器最强大也最容易混淆的特性：

各模式详解

None（无中止）：

  • 装饰器仅在搜索时评估，不会响应条件变化
  • 适用于静态条件（如”是否有武器”）

LowerPriority（中止低优先级）：

  • 当条件从 false 变为 true 时，中止当前正在执行的低优先级分支，抢占执行
  • 典型场景：巡逻时发现敌人 → 中止巡逻，切换到战斗

Self（中止自身）：

  • 当条件从 true 变为 false 时，中止自身所在分支的执行
  • 典型场景：追击敌人时敌人消失 → 中止追击

Both（双向中止）：

  • 根据当前执行位置自动选择 Self 或 LowerPriority
  • 如果正在执行自身分支 → Self
  • 如果正在执行其他分支 → LowerPriority
  • 最灵活但性能开销最大

五、装饰器作用域（Decorator Scope）

5.1 bApplyDecoratorScope

复合节点的 bApplyDecoratorScope 属性控制装饰器的作用域：

  • true：当执行流离开该复合节点时，自动注销其下所有分支的装饰器
  • false（默认）：装饰器保持注册状态

BTComposite_SimpleParallel 默认设置 bApplyDecoratorScope = true，因为并行节点需要在主任务完成时清理后台树的装饰器。

7.3 性能注意事项

  1. 避免过度使用 Both 模式：Both 模式需要额外判断当前执行位置
  2. 使用 ResultChange 而非 ValueChange：减少不必要的搜索触发
  3. 简单条件用 Blackboard 装饰器：比自定义装饰器更高效
  4. 合理设置 FlowAbortMode：只在需要动态切换的装饰器上设置非 None 模式
  5. 装饰器数量控制：每个分支的装饰器数量影响搜索性能
