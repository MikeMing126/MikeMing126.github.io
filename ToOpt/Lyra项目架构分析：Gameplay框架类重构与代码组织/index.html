Lyra 项目架构分析：Gameplay 框架类重构与代码组织

这篇文章围绕 Lyra 示例项目的代码架构展开，讨论以下问题：

  • Lyra 重写了哪些 Gameplay Framework 基础类？继承体系是什么样的？
  • Lyra 的文件夹组织遵循什么原则？
  • UE 模块内部是否需要分 Public/Private？Lyra 为什么不分？
  • GameFeature 插件与主模块的依赖关系是怎样的？
  • 实际项目中应该怎么规划代码结构？

核心结论：Lyra 的架构体现了 Epic 对 UE5 项目组织的最佳实践——按功能领域内聚、极简模块划分、通过 GameFeature 插件实现内容扩展。对于大多数中小型项目，Lyra 的组织方式可以直接参考。

Gameplay 框架类的重写与继承体系

Lyra 重写了 UE 全部 8 个核心 Gameplay 框架类，外加 GameEngine、GameSession、HUD，共 11 个类。重写的核心目的有两个：一是通过 Modular 中间基类 使框架类支持组件化扩展（GameFeature 插件可向其注入组件），二是集成 GAS（Gameplay Ability System） 和团队系统等通用能力。

完整继承体系

继承链中出现了两个重要的中间层：

中间层 来源插件 作用
AModular* 系列 ModularGameplayActors 允许通过 GameFeature 插件向框架类注入组件，无需修改基类代码
ACommonPlayerController / UCommonGameInstance CommonGame 提供通用的 UI 管理策略和平台操作封装

类的放置位置

放置文件夹 包含的类 规律
System/ GameEngine, GameInstance, GameSession, AssetManager, ReplicationGraph 进程级/全局级基础设施
GameModes/ GameMode, GameState, Experience 系统 游戏规则与状态
Player/ PlayerController, PlayerState, LocalPlayer 玩家相关
Character/ Character, Pawn, MovementComponent 角色实体
UI/ HUD 界面相关

TL;DR: Lyra 将全局生命周期的类放在 System/，配对紧密的类（GameMode + GameState、PlayerController + PlayerState）放在同一文件夹，HUD 归入 UI 体系。

按功能领域划分的目录结构

Lyra 采用按功能领域（Feature Domain）划分的方式，而非常见的按代码类型（Class/Component/Interface）划分。

这套组织方式遵循几个核心原则：

同一功能的所有代码放在一起。 Character/ 文件夹中既有 Actor 类（LyraCharacter、LyraPawn），也有 Component 类（LyraHealthComponent、LyraHeroComponent、LyraPawnExtensionComponent），还有 DataAsset 类（LyraPawnData）。这样理解一个功能不需要跨文件夹查找。

UI 按层级再分子目录。 UI/ 目录下进一步按 Basic → Common → Foundation → Frontend 分层，体现控件从底层到具体的层次关系。

极简模块划分。 Source 下只有 LyraGame（运行时）和 LyraEditor（编辑器）两个模块，避免了过度模块化带来的编译时间和依赖管理问题。

模块内部要不要分 Public/Private？

这是一个实际项目中经常遇到的问题。Lyra 的答案是不分——但需要理解它为什么能这样做。

Public/Private 的技术意义

在 UE 的 Unreal Build Tool (UBT) 体系下，Public/Private 不仅仅是分类习惯，而是有编译级别的约束力：

目录 含义 效果
Public/ 接口层 其他模块可以 include 此目录下的头文件
Private/ 实现层 其他模块无法 include，仅当前模块可见

正确使用 Public/Private 带来的好处：

  • 强制封装：明确哪些类是”公开接口”，哪些是”内部实现”，防止其他模块随意依赖内部细节
  • 提升编译速度：Private 中的头文件变化只触发当前模块重编，不会引发依赖模块的连锁重编
  • 规范化：UE 的”新建 C++ 类”向导默认支持这种结构

代价是目录层级更深，且需要手动管理 MODULENAME_API 宏和 Build.cs 中的依赖配置。

这行代码将 LyraGame 的整个源码目录作为公共包含路径暴露给依赖者。原因是 GameFeature 插件需要深度访问 LyraGame 的几乎所有子系统——Character、AbilitySystem、Equipment、Weapons、Messages、Teams……

如果 LyraGame 用了 Public/Private 分层，就会陷入两难：

  • 把大部分头文件放 Public：跟不分几乎没有区别，只是多了一层目录跳转
  • 把一些头文件放 Private：GameFeature 插件就无法访问它们，需要反复调整边界

Lyra 的选择是：既然 GameFeature 和 LyraGame 本质上是一体的——它们是同一套游戏的不同功能切片——那就干脆不做隔离。

什么时候该分，什么时候可以不分？

关键判断标准是你的模块是否作为稳定 API 供外部使用：

不需要分（Lyra 模式）：GameFeature 插件由自己团队开发，与 Gameplay 模块高度耦合，需要深度访问内部类型。这种情况下强行隔离只会增加维护成本。

需要分（严格封装模式）：多团队协作、GameFeature 由外包开发、需要控制插件能访问什么，或者 Gameplay 内部需要自由重构而不影响下游。

对于 GameCore + Gameplay 双模块结构的实际建议：

底层模块 GameCore 用 Public/Private 封装是正确的，但 Gameplay 作为 GameFeature 的直接上游，过度封装只会增加开发摩擦。

插件与模块依赖架构

TL;DR: Lyra 的依赖链是 框架插件 ← LyraGame 本体 ← GameFeature 插件。本体提供骨架，框架插件提供通用基础设施，GameFeature 插件提供可插拔的游戏玩法。

实际项目的代码组织建议

从 Lyra 的实践中可以提炼出几条通用原则：

  1. 按功能领域划分文件夹，而非按代码类型。同一功能的 Actor、Component、DataAsset 放在一起
  2. 全局级类不需要单独文件夹。GameEngine、GameInstance 代码通常很少，放在一个 Core/ 或 System/ 里足矣
  3. 配对紧密的类放在一起。GameMode + GameState、PlayerController + PlayerState 都不需要拆开
  4. 避免”Utils”或”Common”垃圾箱。工具函数应就近放在使用它的功能文件夹中
  5. 底层模块用 Public/Private 封装，上层模块（被自己团队开发的插件深度依赖的）可以不封

总结

Lyra 的项目架构体现了几个关键设计思想：

  • Modular 中间层是架构的关键创新——框架类可以通过插件扩展而无需修改源码
  • 按功能领域内聚而非按代码类型分类——理解一个功能不需要跨文件夹查找
  • 极简模块划分——只有 LyraGame 和 LyraEditor 两个模块，通过 GameFeature 插件实现内容扩展
  • GameFeature 插件与 Gameplay 本体高度耦合——因此不需要 Public/Private 隔离，这是合理的架构选择而非疏忽
  • 底层模块（GameCore 等）仍应使用 Public/Private——因为它们确实需要向下游提供稳定的 API 边界

在实际项目中，建议以 Lyra 的结构为起点，随着项目规模增长再逐步拆分可能膨胀的文件夹（如 System/）。
