UE5 C++ 代码组织方式与编排规则

本文探讨 UE5 引擎源码中的代码组织风格，主要回答以下问题：

  • UE 引擎源码中 public/protected/private 是如何排列的？
  • C++ 没有类似 C# #region 的语法，引擎用什么方式做代码分区？
  • 一个标准的 UE 类头文件应该怎么编排？
  • #pragma region 在 UE 中是否可用、是否应该用？

核心结论： UE 的代码编排哲学是 “按功能分组” 而非 “按访问级别分组”，属性和操作它的方法就近放置，通过注释分隔符提供可读性。#pragma region 虽然可用但不是引擎主流风格。

访问控制的布局规则

TL;DR: 引擎源码不拘泥于”所有 public 放一起”的教科书式排列，而是 按功能分组，频繁切换访问控制。

核心原则如下：

原则 说明
成员变量总在最底部 所有类型的类都遵守此规则，数据成员放在类的最后面
属性和方法就近放置 UPROPERTY 属性和操作它的方法紧邻，而非严格分离”属性区”和”方法区”
访问控制按功能分组 同一功能相关的 public/private/protected 可以交替出现
构造函数在最前面 构造/析构函数总是类体的第一个 public: 段
friend 声明在类最顶部 在第一个访问修饰符之前

代码分区方式

TL;DR: C++ 没有原生的 #region 语法，UE 引擎源码使用三种注释模式来实现代码分区。

/*---...---*/ 块注释分区

这是引擎核心类（如 UObjectBaseUtility、UObject）最常用的分区方式。分区名称居中，用 - 填充两侧，形成视觉上的分割线：

//~ Begin/End XXX Interface 接口覆盖标记

#pragma region 在 UE 中的使用分析

无逻辑影响

#pragma region / #pragma endregion 是 MSVC 的编译器扩展指令，编译器 完全忽略 这两条指令，不会生成任何代码。唯一作用是让 IDE 提供代码折叠功能。

引擎核心几乎不使用

#pragma region 在 UE 引擎核心源码中几乎不使用，仅出现在极少数边缘文件中（如实验性插件 SlateIM）。引擎核心选择注释而非 #pragma region 的原因：

因素 说明
跨平台/跨编译器 #pragma region 是 MSVC 扩展，Clang/GCC 虽静默忽略但不是标准行为
跨 IDE 兼容 注释分隔符在任何编辑器、diff 工具、代码审查工具中都可见可读
Epic 官方编码标准 官方推荐用注释做分区，引擎源码 20+ 年一直保持这种风格
代码即文档 注释分区在纯文本查看时仍然有意义，#pragma region 在非 IDE 环境下是噪音

什么时候可以用？

适合使用 #pragma region 的场景：团队全员使用 Visual Studio / Rider、项目 Windows only、文件很大需要 IDE 折叠导航、团队习惯 C# #region 工作流。

不建议使用的场景：需要跨平台编译、团队使用多种 IDE/编辑器、想与引擎核心风格保持一致、开源项目或需要代码审查。

如果只是想增强可读性，优先采用引擎核心的注释分隔符风格：

它不依赖特定 IDE，在任何环境下都能提供可读性，且与 UE 引擎源码风格完全一致。如果确实需要 IDE 折叠功能，#pragma region 也可以用——它没有任何副作用，只是不属于 UE 的主流风格。
