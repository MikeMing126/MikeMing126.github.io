UE5 RPG 与开放世界游戏架构设计：关卡切换与框架规划最佳实践

基于 UE5.7 源码，本文系统探讨一个核心问题：对于 RPG、箱庭、开放世界等非 FPS 类型的游戏，如何规划关卡切换与基础游戏框架？

具体回答以下问题：

  • UWorld 的定位是什么？ GameMode / GameState / PlayerState / PlayerController 各自的职责边界在哪？
  • LevelStreaming 和 WorldPartition 有什么区别？ 底层架构有何异同？怎么选？
  • World 切换（Travel）时数据怎么活下来？ Seamless Travel 和 Hard Travel 有什么区别？
  • 小房间频繁进出、小游戏玩法切换、副本实例化，这些 RPG 常见场景怎么处理？
  • 多人联机下，A 玩家和 B 玩家在不同关卡，服务器怎么管理？
  • 团队多人协作编辑地图时，两种方案对工作流有什么影响？

核心结论：对于这类游戏，尽量避免 UWorld 的物理切换，改为在同一个 UWorld 下通过 LevelStreaming / WorldPartition 进行流式加载，配合 GameInstanceSubsystem 持久化核心数据、GameMode 内状态机切换玩法模式。大地图用单 UWorld + WorldPartition 是最优解，副本/特殊玩法用独立 UWorld + SeamlessTravel，核心数据全部放 GameInstanceSubsystem 跨 World 持久化。

UE 架构与 RPG 需求的根本矛盾

在深入方案之前，先看清问题的本质——UE 的默认行为与 RPG 需求之间存在三组根本性矛盾：

矛盾 UE 的默认行为 RPG 的需求
World 切换 = 销毁重建 硬切换/无缝切换都会 CleanupWorld() 销毁整个 UWorld 及所有 Actor 小房间进出、小游戏需要快速切换且保留状态
GameMode 决定框架类 GameState、PlayerController、PlayerState 由 GameMode 的类指针决定 小游戏玩法完全不同，但不应该丢失角色进度数据
一个 GameInstance 只有一个活跃 World FWorldContext::ThisCurrentWorld 同一时间只指向一个 World 多人模式下 A 和 B 可能在完全不同的关卡

理解了这三组矛盾，后续的分层方案就有了清晰的指向。

UE5 核心游戏框架

TL;DR: UE5 的四大框架类遵循”信息隐藏 + 职责分离”设计。UWorld 是沙盒容器而非”关卡”，PlayerState 是”所有客户端可见的玩家摘要”而非”完整数据容器”。

UWorld 的定位

从 World.h 源码注释：

The World is the top level object representing a map or a sandbox in which Actors and Components will exist and be rendered.

UWorld 本质上是一个”沙盒容器”，不是一个”关卡”。一个 UWorld 内部可以通过 StreamingLevels 和 WorldPartition 包含任意多的子关卡。引擎的设计意图是：一个逻辑上连续的游戏空间 = 一个 UWorld。

UWorld 继承自 UObject 并实现 FNetworkNotify 接口，内部维护了完整的关卡流送系统：

  • StreamingLevels：TArray<TObjectPtr<ULevelStreaming>> 数组，保存所有流送关卡
  • 通过 AddStreamingLevel / RemoveStreamingLevel / UpdateLevelStreaming 等方法管理流送生命周期

UWorld 持有的核心引用：

四大框架类的职责划分

类 存在于 核心职责
AGameModeBase 仅服务器 定义游戏规则、玩家登录流程、Pawn 生成。持有 GameStateClass、PlayerControllerClass、PlayerStateClass 等类引用
AGameStateBase 服务器+所有客户端 所有玩家都需要知道的游戏全局状态。持有 PlayerArray、同步的服务器时间
APlayerState 服务器+所有客户端 所有玩家都需要知道的”某个玩家的状态”。引擎自身只放约 10 个复制属性（Score、PlayerName、PlayerId 等）
APlayerController 服务器+本机客户端 输入处理、Camera 管理、RPC 通信管道。实现了 IWorldPartitionStreamingSourceProvider

关键观察：PlayerState 被设计为”所有客户端可见的玩家摘要”，不是”玩家的完整数据”。引擎自身只放了最基本属性，这暗示你不应该把所有玩法数据都堆在里面。

关卡加载机制：LevelStreaming vs WorldPartition

TL;DR: LevelStreaming 是”手动挡”——开发者完全控制加载什么、何时加载；WorldPartition 是”自动挡”——引擎根据玩家位置自动管理。两者底层共享同一套 ULevelStreaming 状态机，最核心的差异在于 ULevel 的来源。

LevelStreaming：逻辑驱动的手动分区

将大型世界拆分为多个独立的 .umap 文件，运行时按需动态加载/卸载这些子关卡，它们共享同一个 UWorld。

核心类层次：

状态机（定义于 LevelStreaming.h）：

关键流程：

  1. SetShouldBeLoaded(true) + SetShouldBeVisible(true) 触发
  2. RequestLevel() → LoadPackageAsync() 异步加载 .umap Package
  3. AsyncLevelLoadComplete() → UWorld::FindWorldInPackage() → 取 World->PersistentLevel（即 ULevel）
  4. UWorld::AddToWorld(LoadedLevel) → Levels.AddUnique(Level) 加入世界

WorldPartition：数据驱动的自动分区

整个大世界只使用一个 .umap 文件，引擎自动按空间网格划分为若干 Cell，运行时根据玩家位置动态加载/卸载对应区域。

核心类层次：

关键流程：

  1. UWorldPartitionSubsystem::Tick → StreamingPolicy::UpdateStreamingState
  2. 收集 StreamingSource（玩家位置/摄像机）
  3. RuntimeHash->ForEachStreamingCellsSources() 空间查询决定哪些 Cell 需要加载
  4. Cell::Load() → 动态创建空 ULevel（不是从磁盘反序列化）
  5. IssueLoadRequests() → 异步加载外部 Actor 包并注入到此 ULevel
  6. Cell::Activate() → SetShouldBeVisible(true) → UWorld::AddToWorld()

最核心的架构差异

完整对比

维度 LevelStreaming WorldPartition
地图文件 多个 .umap，每个是完整子世界 单个 .umap，Actor 以 External Actor 形式独立存储
分区方式 手动拆分，开发者决定内容归属 自动基于空间网格划分 Cell
ULevel 来源 从 .umap Package 反序列化 运行时 UWorld::CreateWorld() 动态创建空 ULevel，再注入 Actor
加载粒度 一整个 .umap Cell 级别（一个空间网格内的 Actor 子集）
触发方式 Volume / 蓝图 / 代码手动控制 自动基于 StreamingSource + DataLayer 状态
DataLayer 支持 无原生支持 原生支持，可按逻辑层控制 Cell 加载
编辑器体验 需要手动管理子关卡、手动设置 Transform 连续大世界，所见即所得
LevelStreaming 复用 直接使用 ULevelStreaming 体系 内部复用了 ULevelStreaming 体系，通过 UWorldPartitionLevelStreamingDynamic 桥接

关键共同点：

  1. 两者加载的子 ULevel 都通过 UWorld::AddToWorld() 加入 UWorld::Levels 数组，共享渲染场景、物理场景、导航系统
  2. 底层都走 LevelStreaming 状态机
  3. 都支持异步加载（LoadPackageAsync）
  4. 子 ULevel 的 OwningWorld 都指向主世界 UWorld

World 切换机制

TL;DR: UE 提供两种 World 切换方式。Hard Travel 销毁所有 Actor 并断开网络连接；Seamless Travel 通过两阶段异步加载保留指定 Actor 且网络连接不断开。对于 RPG 游戏，应尽量减少 World 物理切换。

Hard Travel（硬切换）

当 bUseSeamlessTravel 为 false 时走此路径：

  1. 调用 StartToLeaveMap()
  2. 调用 ProcessClientTravel() 通知客户端
  3. 客户端断开连接，重新加载新地图
  4. 所有 Actor 被销毁，重新创建 GameMode / GameState / PlayerController / PlayerState

Seamless Travel（无缝旅行）

当 bUseSeamlessTravel = true 时，核心封装在 FSeamlessTravelHandler 类中。

两阶段加载过程：

  1. 阶段一：加载过渡地图（Transition Map）

    • 广播 OnSeamlessTravelStart 事件
    • 如果已在默认地图，直接加载目标；否则先加载过渡地图

  2. 阶段二：加载目标地图

    • 过渡地图加载完成后，异步加载最终目标地图
    • 再次执行 Actor 迁移和 CopyWorldData

保留了哪些 Actor？ AGameModeBase::GetSeamlessTravelActorList() 默认保留所有 PlayerState，在过渡阶段还保留 GameMode、GameState、GameSession。自动保留所有 PlayerController 及 Role < ROLE_Authority 的 Actor。

CopyWorldData — 网络连接不断的核心：

关键点：Seamless Travel 时网络连接不会断开。 NetDriver 被直接搬到新 World，所有 RPC 通道保持活跃。对玩家来说只是一次短暂的加载画面。

Seamless Travel 全景图

关键决策因素

  • bUseSeamlessTravel 属性决定是否使用无缝旅行
  • 服务器运行超过 48 小时后自动回退到硬切换（防止 TimeSeconds 溢出）
  • URL 参数 ?SeamlessTravel / ?NoSeamlessTravel 可强制覆盖

数据持久化策略

TL;DR: 三层持久化方案——GameInstanceSubsystem 最强（跨所有 World 切换存活）、Seamless Travel Actor 迁移中等（仅 Seamless 时有效）、URL Options 最轻量。

三层持久化架构

GameInstance 与 Subsystem 生命周期

UGameInstance 是跨 World 生命周期的核心对象，不属于任何 UWorld，挂在 FWorldContext 上。在 CopyWorldData() 中 GameInstance 被显式地从旧世界”搬”到新世界。

Subsystem 生命周期层级：

层级 基类 生命周期 用途
Engine UEngineSubsystem 进程级 全局单例
GameInstance UGameInstanceSubsystem 游戏实例级 跨 World 持久化数据
World UWorldSubsystem World 级 随 World 创建/销毁
LocalPlayer ULocalPlayerSubsystem 本地玩家级 随本地玩家创建/销毁

数据分层最佳实践

数据类型 放在哪 原因
其他玩家需要看到的（等级、外观、状态） PlayerState 引擎自动复制到所有客户端
仅自己需要知道的（背包、任务、详细属性） GameInstanceSubsystem 跨 World 存活，不浪费带宽
服务器需要但客户端不需要的（AI决策数据） 服务器端自定义组件 不复制
全局游戏进度 GameState 所有客户端可见

PlayerState 的正确定位

PlayerState 只放”所有玩家可见的最小摘要”，引擎自身只定义了约 10 个复制属性。RPG 核心数据必须放在 UGameInstanceSubsystem 中：

世界切换时的数据流向

  • Seamless Travel 时：GameMode / GameState / PlayerState 通过 GetSeamlessTravelActorList() 保留；PlayerState 的关键属性通过 SeamlessTravelTo() 复制；GameInstanceSubsystem 完全不受影响
  • Hard Travel 时：只有 GameInstance 层级以上的数据存活；全部框架类销毁重建；通过 GameInstanceSubsystem 手动恢复

RPG 实战场景

TL;DR: 尽量减少 UWorld 物理切换，用 Level Streaming + GameInstanceSubsystem + GameMode 内状态机解决绝大多数场景。

小房间频繁进出

不要为每个小房间创建单独的 UWorld。 用 Level Streaming 在同一个 UWorld 内动态加载/卸载子关卡，GameMode、GameState、PlayerController 全部存活，网络连接不断开。

Level Streaming 不会销毁 UWorld，只是在 UWorld::Levels 数组中增删 ULevel。LoadedNotVisible 状态可以用来预加载——关卡已在内存但不可见，进出房间体验更流畅。

World Partition 替代方案：将小房间分配给一个 Data Layer，进门时 Activate 房间 Data Layer，出门时设为 Unloaded，引擎自动处理加载和资源回收。

小游戏玩法切换

不要切换 GameMode 类。 小游戏的挑战是玩法完全不同（角色、UI、规则变化），但又不能丢失主游戏状态。

推荐方案：GameMode 内的玩法模式状态机：

原因：

  1. 切换 GameMode 类 = 切换 World，代价太大
  2. 小游戏只是”规则不同”，不是”网络框架不同”
  3. PlayerController 可以动态切换输入映射（EnhancedInput + IMC），不需要重建

如果小游戏需要独立关卡内容，用 Level Streaming 加载小游戏关卡，卸载主游戏大场景资源。

Modular Gameplay 思路：进入小游戏时，动态给 PlayerController 或 Pawn 挂载一个 GameFrameworkComponent（如 UVehicleLogicComponent）来接管输入逻辑，玩法结束后移除，不需要销毁 PlayerController 实例。

多人联机下的关卡管理

TL;DR: UE 的网络架构默认是一个服务器 UWorld，所有玩家在同一个 World 里。LevelStreaming 通过 RPC 同步可见性，WorldPartition 客户端自主决策但默认服务器加载所有 Cell。

LevelStreaming 的多人行为

服务器和客户端各自独立管理 StreamingLevels 列表，通过 RPC 同步可见性状态：

关键规则：

  • 服务器必须加载所有参与网络复制的 Level——如果服务器没有加载某个 StreamingLevel，该 Level 中的 Actor 无法参与网络复制
  • 客户端默认不能自主决定让 Level 可见，必须等服务器确认
  • Player A 在 Room A、Player B 在 Room B 时，服务器需同时加载两个 Level

WorldPartition 的多人行为

WorldPartition 的 CanReplicateStreamingStatus() 返回 false，不使用传统的 Level 可见性复制机制，客户端自主根据 StreamingSource 决定加载。

服务器行为模式：

模式 CVar 服务器行为
默认 wp.Runtime.ServerStreaming=0 加载所有非 DataLayer Cell
ServerStreaming 启用 =1, StreamingOut=0 跟随客户端 StreamingSource，但加载后永不卸载
ServerStreaming + StreamingOut =1, StreamingOut=1 完全跟随客户端 StreamingSource，可卸载

DataLayer 的网络同步

  • Client-Only DataLayer：必须在客户端调用
  • Server-Only DataLayer：必须在服务端调用
  • 普通 Runtime DataLayer：必须在服务端调用，状态自动复制到客户端

多人场景对比

场景 LevelStreaming WorldPartition
A/B 玩家在不同区域 服务器同时加载两个 Level；客户端各自加载 服务器加载所有 Cell（默认）或仅加载有玩家的 Cell（ServerStreaming）
服务器内存压力 可控 默认极高，需启用 ServerStreaming 优化
网络复制 Level 中的 Actor 天然支持 服务器需先加载 Cell 才能 Actor 复制
延迟/预加载 LoadedNotVisible 状态可预加载 Cell 支持预加载

推荐方案：Level Streaming + 空间隔离

服务器加载所有玩家需要的 Streaming Level，每个客户端只加载自己视野范围内的 Level。UE 的网络同步基于 Actor 是否”相关（Relevant）”——如果 A 在房间里，B 在森林里，服务器会自动停止向 A 同步森林里的 Actor 变化。

极端方案：多 World 服务器

UE 源码中 FWorldContext 的注释暗示了这个方向：

“By default we have 1 track that we load and unload levels on. Adding a second context is adding a second track.”

但这需要服务器端创建多个 UWorld、通过 GameInstanceSubsystem 做跨 World 数据同步、玩家跨 World 时迁移 PlayerController。非常复杂，除非你有 MMO 独立副本这种需求，否则不推荐。

团队协作与编辑器工作流

TL;DR: 传统 .umap 是二进制单体文件，一人修改全图锁定；World Partition 通过 OFPA 将每个 Actor 拆为独立文件，实现真正的并行开发。

传统 .umap 的局限

传统关卡文件是一个巨大的二进制单体文件。修改任何一个 Actor，整个 .umap 都会被标记为已修改。在版本控制系统下，一旦一名开发者签出该地图，其他人都会被锁定。二进制文件无法合并，必然导致其中一人的工作被覆盖。

传统对策是将地图拆分成几十个子关卡，由不同的人负责不同的子关卡文件。

World Partition 的 OFPA 方案

World Partition 引入 OFPA（One File Per Actor） 机制，.umap 文件不再存储 Actor 的具体数据，每个 Actor 都在 ExternalActors 文件夹中生成一个独立的外部文件。

协作优势：

  • 独立修改：开发者 A 修改”路灯 A”，开发者 B 修改”路灯 B”，对应不同文件，可同时提交互不干扰
  • 无感合并：版本控制系统只需处理独立 Actor 文件的增删改
  • Outliner 协作：关卡中的文件夹层级结构也是外部对象存储的，允许多用户同时调整目录结构

协作特性对比

特性 传统 .umap World Partition
文件争用 严重。一人修改，全图锁定 极低。仅锁定当前编辑的 Actor
Source Control 必须签出整个 .umap 自动签出选中的 Actor 对应的小文件
合并风险 高。二进制合并极易损坏数据 低。Actor 之间数据解耦
数据同步 保存并提交后他人才能看到 支持 Multi-User Editing 插件实现秒级同步

最佳实践

  • 启用 OFPA：创建”Open World”模板会自动启用；旧地图可在 World Settings 中勾选 Use External Actors
  • 注意非 OFPA 内容：关卡蓝图逻辑仍然存储在主关卡文件中，多人同时修改会产生冲突。建议将复杂逻辑写在 Actor 组件或子系统中
  • Multi-User Editing（高级）：部署虚幻内置的 Multi-User Editing Server，可在 WP 基础上实现实时内存级场景同步

推荐架构方案

TL;DR: 大地图用单 UWorld + WorldPartition，副本/特殊玩法用独立 UWorld，World 切换走 SeamlessTravel，核心数据放 GameInstanceSubsystem，PlayerState 只承担复制摘要。

架构总览

核心设计原则

决策 原因
大世界用单 UWorld + WorldPartition 引擎原生设计如此，无缝体验最佳
副本/特殊玩法用独立 UWorld 需要不同 GameMode 规则时才切 World
World 切换走 SeamlessTravel 网络不断开，玩家体验好
核心数据放 GameInstanceSubsystem 跨 World 存活，不依赖 SeamlessTravel
PlayerState 只放复制摘要 符合引擎设计意图，不浪费带宽
PlayerController 处理输入和 RPC 这是本职工作，不需要包揽一切
小游戏用 GameMode 内状态机 避免切换 World，保留主游戏状态
小房间用 Level Streaming 不销毁 UWorld，进出快速

选型决策树

按游戏类型的推荐方案

RPG（角色扮演游戏）：LevelStreaming 为主 + 适度 DataLayer。城镇是离散独立场景用 StreamingLevel，室内房间动态加载卸载，副本用 LoadLevelInstance 动态实例化。

箱庭类（如塞尔达、原神）：WorldPartition + DataLayer + LevelStreaming 补充。大世界用 WP 自动空间分区，天气/季节用 DataLayer 切换，地下城/秘境用 LoadLevelInstance。

大世界 / MMO：WorldPartition + ServerStreaming + DataLayer + 架构补充。必须启用 wp.Runtime.ServerStreaming + wp.Runtime.ServerStreamingOut 让服务器按需加载，跨服/分区需要自研 Zone/Cluster 系统。

注意事项与常见陷阱

APlayerState 的生命周期陷阱

APlayerState 随 UWorld 生灭。在 Level Streaming 场景下不会丢失（World 不变），但在 World 切换场景下一定会丢失。永远不要在 APlayerState 里放 RPG 核心数据，它只放网络身份信息（玩家名、Team ID、Score 等）。

Seamless Travel 保留的 Actor

可以通过 GetSeamlessTravelActorList() 添加需要保留的 Actor，但不要滥用——保留太多 Actor 会导致内存压力。

网络复制与 Streaming Level

服务器端需要加载所有相关玩家所在的 Streaming Level 才能正确处理网络复制。如果服务器没有加载某个 Level，该 Level 中的 Actor 不会被 Tick，也不会复制给客户端。

World Partition 的网络限制

World Partition 在服务器端会根据所有玩家位置加载 Cell。服务器内存 = 所有玩家视野范围之和。如果玩家分散得很开，服务器内存压力会很大。对于 RPG 这种玩家可能分布在各处的场景，传统手动管理的 Streaming Level 可能比 World Partition 更可控。

关卡蓝图与协作冲突

关卡蓝图逻辑存储在主关卡文件中，多人同时修改会产生冲突。建议将复杂逻辑写在 Actor 组件或子系统中，避免在 Level Blueprint 中放置重要逻辑。

总结

对于 RPG / 箱庭 / 大世界游戏，核心原则可以概括为三句话：

  1. 避免 World 切换，用 Level Streaming + GameInstanceSubsystem + GameMode 内状态机解决绝大多数场景
  2. 大地图用单 UWorld + WorldPartition，需要不同 GameMode 规则的场景才用独立 UWorld + SeamlessTravel
  3. 核心玩法数据全部放 GameInstanceSubsystem，PlayerState / PlayerController 只承担引擎赋予的本职工作

这种架构能很好地支持模块化——增加新玩法只需要写新的组件和输入映射，通过状态机切换即可。参考 Lyra 的 Experience 系统，它是这种”壳架构”的终极进化版。
