UE GameFeature 与 Module 对比

对GameFeature和Module进行分析。同时考虑其本质：程序集，探讨和Unity对应的程序集的异同和实践方案。

Module

具体的内容可以看到这篇文章：

UE-Module

一般Plugin，也会有对应的代码模块。

本质定义

模块是编译边界，不是逻辑边界

Module 是编译期与运行期的代码组织单元，与资产（Asset）无强制绑定关系。

  • 由 .Build.cs 定义，UBT 编译为独立共享库（.dll/.so）
  • 必须实现 IModuleInterface（通过 IMPLEMENT_MODULE 宏注册）
  • 加载由 FModuleManager 管理，支持运行时动态加载

与资产的关系：

  • 无引擎级强绑定：资产通过包路径（/Game/...）寻址，与模块名无关
  • 工程惯例：模块根目录下创建 Content/，UBT 自动识别为关联资源（仅为打包与路径组织约定）
  • 源码体现：UnrealBuildTool 扫描模块目录下的 Content，但资产注册/Cook/加载由 ContentPipeline 独立处理

划分原则

原则 说明
单一职责 一个模块只负责一个清晰的功能域
依赖单向 严格遵循 Base/Core → Gameplay → Feature 的依赖方向，禁止循环依赖
API 显式隔离 .Build.cs 中严格区分 PublicIncludePaths（对外暴露）与 PrivateIncludePaths（内部实现）
加载边界清晰 按需加载（Runtime）、仅编辑器加载（Type=Editor）、或启动必加载

优缺点

优点：

  • 编译加速：UBT 仅重编译修改的模块及其依赖项
  • API 边界清晰：通过 Public/Private 头文件隔离，防止内部实现被外部耦合
  • 运行时可控：支持 FModuleManager::LoadModule 动态加载/卸载
  • 团队协同：模块即代码所有权边界，减少 Git 合并冲突

缺点：

  • 架构开销：需维护 .Build.cs、模块接口、依赖声明，小型项目易过度设计
  • 通信成本：跨模块调用需通过接口、委托或事件总线，增加间接层
  • 循环依赖禁令：UE 不允许模块循环依赖，设计失误需重构解耦

示例

  • 官方古代山谷:仅项目一个。
  • 官方Lyra:区分Editor和Game。
    大型项目可以再考虑区分Core和Gameplay。

GameFeature Plugin（GFP）

从实践和迭代的角度出发，最好不要轻易用这个。除非某个对应GameFeature的内容后续迭代不会依赖其他的GameFeature。

但是从DLC的角度来说，确实是一个不错的选择。动态注入的方式，使得本体无需考虑注入的内容。

设计思路：依赖反转

传统插件系统由核心工程调用插件（Core → Plugin）。GameFeature 采用依赖反转：

  • 隔离性：核心工程对 GFP 一无所知，插件自行定义对核心工程的修改
  • 非侵入性：通过 GameFeatureData 资源声明式执行操作：
    • 向现有 Actor 添加组件
    • 注册新的输入绑定（Enhanced Input）
    • 向核心工程 UI 槽位注入 Widget
    • 修改全局 DataTable 或 Asset Manager 列表
  • 运行时动态开关：支持在游戏运行过程中加载、激活或卸载

优缺点

优点：

  • 高度解耦：降低核心代码复杂性，防止”牵一发而动全身”
  • 清理方便：禁用插件并删除对应文件夹，核心工程无残留
  • 内存优化：仅在特定条件/地图下加载功能
  • 协作友好：功能边界清晰，适合大规模团队

缺点：

  • 复杂度增加：需理解 GameFrameworkComponentManager 和组件初始化生命周期（Init States）
  • 调试门槛：逻辑分散在各插件中，跨插件冲突排查困难
  • 编辑器限制：PIE 多玩家测试时 GFP 全局激活，一个玩家触发加载会影响所有同进程实例

GameFeature 间依赖与冲突

依赖规则

不建议 GFP 互相依赖。设计核心是单向依赖：BaseGame ← GameFeature。

层面 现实情况
插件层 .uplugin 支持声明依赖，引擎保证加载顺序
GameFeature 层 加载（Load）与激活（Activate）分离，激活顺序不解析依赖图
热插拔风险 B 被停用时，A 持有的引用变为悬空状态，引擎不自动级联处理

推荐架构：

  • Shared Plugin：将公共接口、基础组件抽离为独立共享插件，所有 GFP 依赖该插件
  • BaseGame 扩展契约：由 BaseGame 定义扩展协议（UINTERFACE、DataAsset 配置表、自定义 GameFeatureAction），GFP 通过实现这些协议与 BaseGame 交互

多 GFP 冲突风险

GFP 系统是”声明式注入”，引擎不自动做冲突检测或合并：

冲突类型 表现 规避建议
组件注入冲突 多个 GFP 向同一 Actor 注入相同类型组件，生成多个实例 用 HasComponent<T>() 预判；设计为可叠加或互斥逻辑
Enhanced Input 冲突 同名 InputAction 按优先级/注册顺序覆盖 统一命名前缀；指定唯一 Priority
数据表冲突 多个 GFP 向同一 DataTable 插入相同 Key 使用命名空间隔离 Key（如 GF_Weapon_Sword）
UI 扩展冲突 向同一 Slot 注入 Widget，未处理层级 BaseGame 提供 Slot 优先级策略
Gameplay Tag 冲突 多个 GFP 修改同一全局 Tag 遵循 Tag 层级规范；状态修改走事件总线

冲突预防策略：

  1. 命名空间隔离：所有 GFP 内部资产路径、类名、InputAction、Key 必须带插件前缀
  2. 接口优于继承：GFP 注入组件应实现接口，BaseGame 通过接口调用
  3. 自定义 UGameFeatureAction：激活前做冲突校验
  4. 调试工具：gamefeature.list、gamefeature.activate <Name>、LogGameFeature

Unity程序集,UE模块,面向接口编程的理念

核心理念

两者核心理念高度一致，都遵循”契约先行 → 依赖声明 → 编译隔离 → 运行时解耦”。但语言特性（C# vs C++）、引擎底层架构不同，实现与侧重点有显著差异。

颗粒度差异

Unity .asmdef 颗粒度远小于 UE Module，不应照搬 Unity 模式：

维度 Unity .asmdef UE Module
定义成本 JSON 配置，秒级创建 需实现 IModuleInterface、写 .Build.cs、配置 PCH、注册 UHT
构建管线 Roslyn 增量编译，轻量 UBT → UHT → C++ 编译 → DLL 链接 → 符号导出合并
链接开销 托管程序集，无 native 导出表压力 每模块独立 DLL，Windows 下 PE 导出表膨胀
维护成本 IDE 自动处理 手动维护依赖声明，循环依赖直接阻断编译

结论：UE 模块是编译边界而非逻辑解耦工具。模块数量每增 1 个，UBT/UHT 启动时间、增量编译判断成本、CI/CD 缓存压力非线性上升。

具体对比

有必要再看 一般理解理论即可

Unity + C# 特点

维度 说明
程序集划分 .asmdef（JSON）声明编译边界，自动阻断循环依赖
接口编程 原生 C# interface，零额外开销；配合 DI 容器（VContainer/Zenject）
依赖注入 运行时动态解析，构造函数/字段注入 + ScriptableObject 配置
编译迭代 Roslyn 增量编译极快，修改某程序集仅重编该单元及下游
惯用模式 interface + DI Container + Event Bus + ScriptableObject 数据驱动

UE + C++ 特点

维度 说明
模块划分 .Build.cs（C# 脚本）声明编译边界，UBT 编译为动态库
接口编程 UINTERFACE + 纯虚基类（带反射/蓝图支持）；纯 C++ 抽象类（无反射）
依赖管理 编译期严格声明：PublicDependencyModuleNames / PrivateDependencyModuleNames
运行时通信 USubsystem 服务注册 + 多播委托 + UInterface 执行器
编译迭代 UBT + UHT 预处理，增量编译较快但首次/全量较慢
惯用模式 UINTERFACE + USubsystem + Delegates + UDataAsset + GameFeature

核心差异对比

对比项 Unity + C# UE + C++
边界定义文件 .asmdef（JSON） .Build.cs（C# 脚本，UBT 驱动）
接口本质 原生语言特性，零反射开销 UINTERFACE 带反射/BP 支持；纯抽象类无反射
解耦方式 DI 容器 / Service Locator / SO USubsystem / UInterface / 委托 / DataAsset
依赖检查时机 编辑器保存时 + 编译期拦截 UBT 编译期严格拦截（Circular dependency）
蓝图集成 需手动封装或第三方插件 UINTERFACE 原生支持蓝图调用
架构重心 轻量、灵活、运行时 DI 严谨、编译期约束强、与引擎子系统深度绑定

UE 中的接口编程

C++ 没有语言层面的 interface，UE 通过 UINTERFACE 宏生成双类结构：

  • C++ 类通过 public IMyInterface 继承，通过虚函数表实现运行期动态分发
  • 限制：UINTERFACE 不能包含成员变量、不能独立实例化（必须附加到 UObject/AActor 派生类）

最佳实践与决策指南

模块最佳实践

实践 说明
Public/Private 物理隔离 仅将其他模块需要调用的接口类、结构体、Delegate 放在 Public
API 宏克制使用 仅 Public 目录下需被跨模块访问的类/函数才加 MYMODULE_API，过度暴露增加链接时间
跨模块通信通过接口 用 UInterface 或委托减少硬依赖（#include 对方头文件）
类型划分 Runtime（游戏核心）、Editor（编辑器工具）、Developer（调试构建）

颗粒度划分建议（工业标准范式）

判断是否该拆分模块：

  • 功能可独立复用 / 跨项目迁移 → 拆分
  • 依赖方向严格单向，无循环风险 → 拆分
  • 团队需按功能域分配代码权限 → 拆分
  • 仅为”代码分类”或”小功能隔离” → 用 namespace + 内部接口即可

过度细分模块的风险

风险 表现 规避方案
链接爆炸 模块越多，链接器符号解析越慢 控制模块数 ≤5，优先用内部解耦
循环依赖 A→B→A 阻断编译 依赖图保持树状，用接口切断反向依赖
维护负担 每个模块需维护 Build.cs/PCH/导出宏 新建前问：是否真的需要独立编译边界？
打包限制 主机平台对 DLL 数量有限制 合并低频调用的小模块
跨模块调用开销 DLL 导入/导出符号开销 合理合并高频互调模块

解耦组合拳（模块内实现细粒度解耦）

效果：修改实现类 → 仅重编该模块；调用方通过接口交互 → 零耦合；策划改 DataAsset → 无需重编即可切换逻辑。

决策速查表

需求场景 推荐方案 关键理由
基础工具/全局接口 Core 模块 高频引用，变更少，适合作为依赖锚点
主玩法逻辑 Game 模块 + namespace 强耦合、高频迭代，跨模块调用增加间接成本
独立可复用系统 独立 Plugin（1 模块） 需 .uplugin 开关、跨项目分发、依赖隔离
赛季活动 / DLC GameFeature Plugin 运行时动态激活、声明式注入、不污染 Core
编辑器扩展 Editor 模块（Type=Editor） 不进 Runtime 包体，独立编译
模块内逻辑解耦 UINTERFACE + Subsystem + DataAsset 零构建成本，运行期灵活，蓝图友好

自检清单

新建模块/插件前，先问自己：

  • 这个功能是否会被其他项目复用？→ 是 → 考虑独立 Plugin
  • 是否需要运行时动态加载/卸载？→ 是 → 考虑 GameFeature
  • 是否仅编辑器期使用？→ 是 → 用 Type=Editor 模块
  • 修改它是否会导致全项目重编？→ 是 → 检查是否该抽离接口到 Core
  • 依赖图是否出现环？→ 是 → 用接口 + Subsystem 切断反向依赖

核心原则总结

  • 模块是编译边界，不是逻辑边界 → 粗粒度划分（3~5 个），靠接口 + Subsystem 实现细粒度解耦
  • 依赖必须单向 → 用 UINTERFACE 切断反向编译依赖，用 Subsystem 管理运行期注册
  • 能不放模块就不放 → 新建模块前问：是否真的需要独立编译/打包/热插拔？
  • 契约前置，实现后置 → 接口放 Core/Public，实现放 Feature/Private，调用方只依赖接口指针
  • 架构是演进而非设计出来的 → 先用 namespace + UINTERFACE 在单模块内做好解耦，编译时间成为瓶颈时再升级为独立模块
